# 剧集台账与人工资源替换设计

## 读者与目标

本文面向负责实现和维护 Auto-RSS 的工程人员。读完后，应能够在不依赖下载历史、qBittorrent 任务或磁盘文件存在性的前提下，实现按剧集管理收藏状态，并确保同一剧集的资源变化只由用户人工决定是否替换。

## 背景

当前系统主要通过下载记录推断某集是否已经拥有，并允许以下流程自动替换已有资源：

- 定时 RSS 检查发现同语言的更高版本资源时，可能删除旧 qBittorrent 任务及文件并创建新任务。
- 手动“采集剧集”发现同一集的新资源时，可能删除旧下载记录并重新下载。
- RSS 地址变更后，订阅继续沿用原有发布时间水位线，但系统没有独立记录“这一集已经拥有”和“新源提供了不同资源”这两个事实。

这使剧集状态与下载任务、文件和资源版本耦合。用户清理下载历史、删除 qBittorrent 任务、移动媒体文件或更换 RSS 源后，系统可能失去可靠的拥有状态，或者在未经确认时替换资源。

## 目标

- 以“订阅 + 相对集数”为唯一身份管理每一集。
- 简中、繁中、双语、字幕组、分辨率、版本号、hash 和资源地址都不产生第二份自动收藏。
- 下载并完成重命名后，明确将该集标记为已下载。
- 允许用户在没有下载任务和文件的情况下手动标记某集已下载。
- 已下载剧集出现不同资源时只建立待人工处理的候选，不自动下载、删除或替换。
- RSS 地址变更时保留剧集台账，并安全发现新源中的资源差异。
- 删除下载历史、qBittorrent 任务或磁盘文件时，不自动改变剧集拥有状态。
- 人工替换采用先完成新资源、再删除旧资源的顺序，避免替换失败导致丢集。
- 降低通过扫描硬盘推断剧集状态的必要性和默认磁盘访问压力。

## 非目标

- 不为同一集长期管理多语言、多字幕组或多画质收藏。
- 不自动判断哪个字幕组、版本或分辨率更好。
- 不把剧集台账作为文件存在性的实时证明。
- 不在本次设计中引入后台全盘扫描、媒体指纹或文件内容校验。
- 不改变合集种子作为独立下载入口的现有定位；合集内容的逐集建账需要后续单独设计。

## 核心概念

### 相对集数

剧集台账使用季度内的相对集数作为 `episode`。RSS 和现有下载记录中的原始集号继续保留，转换规则为：

```text
relative_episode = original_episode - episode_offset
```

当偏移为 170 时，原始第 171 集对应台账第 1 集。转换结果小于等于 0 的条目不进入本季度台账。

### 剧集台账

剧集台账表达“用户是否已经拥有或明确不需要这一集”，不表达磁盘文件当前是否存在。每个订阅的每个相对集数最多只有一条记录。

新增 `subscription_episodes` 表：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `subscription_id` | 所属订阅 |
| `episode` | 相对集数 |
| `status` | 剧集状态 |
| `active_download_id` | 当前代表该集资源的下载记录，可为空 |
| `active_torrent_hash` | 当前资源 hash，可为空 |
| `active_torrent_url` | 当前资源地址，可为空 |
| `active_title` | 当前资源原始标题，可为空 |
| `status_source` | 状态来源：自动流程、用户操作或迁移 |
| `downloaded_at` | 首次确认已下载的时间，可为空 |
| `created_at` / `updated_at` | 审计时间 |

数据库必须对 `(subscription_id, episode)` 建立唯一约束。`active_download_id` 是可选关联，不是台账生命周期的所有者；删除下载记录时必须将关联置空，而不能级联删除台账。当前资源的 hash、URL 和标题保存在台账中，删除下载历史后仍然保留，用于识别后续 RSS 中出现的是相同资源还是替代候选。

### 资源候选

资源候选表达“RSS 中发现了与当前剧集资源不同、需要用户判断的替代资源”。新增 `episode_resource_candidates` 表：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `subscription_episode_id` | 对应剧集台账 |
| `torrent_hash` | 候选种子 hash |
| `torrent_url` | 候选资源地址 |
| `title` | RSS 原始标题 |
| `fansub` / `language` | 供人工判断的资源信息 |
| `pub_time` | RSS 发布时间 |
| `source_rss_url` | 发现候选时使用的 RSS 地址 |
| `status` | `pending`、`kept_existing`、`replacing`、`accepted`、`accepted_cleanup_failed`、`failed` |
| `failure_reason` | 替换失败原因，可为空 |
| `staged_path` | 新资源替换暂存路径，可为空 |
| `old_resource_path` | 旧资源原路径，可为空 |
| `rollback_path` | 旧资源回滚备份路径，可为空 |
| `final_path` | 新资源正式路径，可为空 |
| `replacement_stage` | 替换阶段，用于崩溃恢复 |
| `created_at` / `updated_at` | 审计时间 |

候选按优先使用 hash、缺少 hash 时使用规范化资源地址的方式去重。同一候选可重复出现在 RSS 中，但只能保留一条待处理记录。

## 状态模型

剧集状态定义为：

- `missing`：当前缺失，允许 RSS 自动创建下载任务。
- `downloading`：已经有该集的活动下载任务，不允许创建第二个自动任务。
- `downloaded`：下载和重命名流程已经成功完成。
- `marked_downloaded`：用户手动声明已拥有，不要求存在下载任务或文件路径。
- `ignored`：用户明确不需要该集，不自动下载，也不为普通 RSS 差异创建待处理候选。

状态转换规则：

```text
无记录或 missing
  ├─ 自动创建下载成功 → downloading
  ├─ 用户标记已下载   → marked_downloaded
  └─ 用户忽略         → ignored

downloading
  ├─ 下载和重命名成功 → downloaded
  ├─ 任务失败或取消   → missing
  ├─ 用户标记已下载   → marked_downloaded
  └─ 用户忽略         → ignored

downloaded / marked_downloaded / ignored
  └─ 用户恢复为缺失   → missing
```

只有明确的用户操作可以把 `downloaded`、`marked_downloaded` 或 `ignored` 恢复为 `missing`。清理历史、删除种子、文件缺失、RSS 换源和候选发现都不得隐式执行该转换。

## 自动 RSS 处理

RSS 条目先按订阅的偏移规则转换为相对集数，再查询剧集台账：

| 台账状态 | 自动处理 |
| --- | --- |
| 无记录 / `missing` | 通过过滤条件后创建下载任务，并写为 `downloading` |
| `downloading` | 不重复下载；资源不同则建立待人工候选 |
| `downloaded` | 不自动下载；资源不同则建立待人工候选 |
| `marked_downloaded` | 不自动下载；资源不同则建立待人工候选 |
| `ignored` | 直接跳过，不建立普通候选 |

资源是否不同按以下顺序判断：

1. 两边都有 torrent hash 时，hash 不同即为不同资源。
2. 任一方缺少 hash 时，比较规范化后的资源地址。
3. 当前台账没有资源 hash 和地址时，已下载或手动标记状态下遇到 RSS 资源也视为人工候选，不自动采用。

标题、语言、字幕组、分辨率或 `v2/v3` 只用于展示，不参与自动替换决策。系统不再调用现有语言版本替换逻辑，也不再在手动采集时删除同集旧记录。

## RSS 地址变更

更新订阅 RSS 地址时：

- 保留订阅 ID、剧集台账、下载历史和现有资源关联。
- 记录 RSS 地址已经变化，并将该订阅标记为需要新源基线同步。
- 不立即自动下载新源当前列表中的历史条目。

订阅增加明确的 `rss_baseline_pending` 状态。只有规范化后的 RSS 地址发生实际变化时才设置该状态；普通订阅字段编辑不触发基线同步。

新源首次成功同步时执行基线对账：

1. 对已有台账的集数比较资源；资源不同则建立待人工候选。
2. 对新源中台账没有记录的历史集数，只建立 `missing` 台账记录，不创建下载任务。
3. 将新源可见的最新发布时间写为新的增量水位线。
4. 基线同步完成后，后续发布时间超过新水位线且状态为 `missing` 的新集才进入自动下载。

这样既不会因为沿用旧源水位线而遗漏新源候选，也不会因为换源一次性回灌整季历史资源。用户可以在换源后的剧集列表中批量标记已有集，或对确实缺失的集执行人工采集。

如果 RSS 条目没有可用发布时间，换源基线仍按本次抓取快照完成对账；后续依靠候选去重和剧集台账防止重复下载。

## 下载、重命名与完成标记

自动创建下载任务和台账更新必须保持一致：

- 下载任务创建成功后，台账进入 `downloading`，关联该下载记录，并保存当前资源的 hash、URL 和标题。
- 下载失败、任务被用户取消或重试最终失败时，只有仍关联该任务的台账才能恢复为 `missing`。
- 下载完成但重命名失败时，不得标记为 `downloaded`。台账保持 `downloading`，由现有重试或人工整理流程继续处理。
- 重命名成功并持久化最终路径后，在同一事务中把台账标记为 `downloaded`，记录 `downloaded_at`、`active_download_id` 和当前资源身份。
- 订阅关闭重命名功能时，下载完成本身视为该订阅配置下的完整流程，可以直接标记为 `downloaded`。

重复的完成事件必须幂等，不能覆盖用户已经设置的 `marked_downloaded` 或 `ignored` 状态。

## 人工标记与批量管理

每个订阅提供剧集列表，至少支持：

- 单集或批量标记为已下载。
- 单集或批量恢复为缺失。
- 单集或批量设为忽略。
- 查看该集当前下载关联和待处理资源候选。
- 对待处理候选选择“保留现有资源”或“使用新资源”。

“标记已下载”只修改台账，不创建虚假下载记录，不访问文件系统。“恢复为缺失”只改变后续自动决策，不自动删除当前下载任务或媒体文件；存在活动任务时，界面应要求用户先明确处理该任务，避免台账与任务竞争。

订阅的 `current_episode`、完成进度、缺集列表和完结判断改为从台账派生：

- `downloaded`、`marked_downloaded` 和 `ignored` 视为不缺失。
- `downloading` 视为处理中，不创建重复任务，但不算最终已下载。
- 连续进度按从第 1 集开始连续不缺失的最大集数计算；不能再用台账中的最大集数假设中间集均已拥有。

现有订阅汇总字段继续保留为缓存和兼容 API，但由台账统一刷新，不再作为事实来源。台账保存相对集数，而兼容字段继续保存原始集号；写回 `current_episode` 或 `latest_episode` 时必须加回 `episode_offset`，保持现有 API 语义不变。

## 人工资源替换

人工选择“使用新资源”后执行以下流程：

1. 将候选标记为 `replacing`，但保持原剧集为 `downloaded` 或 `marked_downloaded`，并保留旧资源关联。
2. 使用候选资源创建独立的新下载记录；该记录标记为人工替换任务，不改变正常 RSS 自动决策。
3. 将新资源下载并整理到独立的替换暂存目录。暂存路径不得与旧资源最终路径相同，也不得覆盖旧文件。
4. 确认新资源下载完整、重命名结果有效且暂存文件可用。
5. 如果旧文件路径仍受系统跟踪，先把旧文件原子移动到同文件系统的回滚备份路径，再把暂存文件原子提升到正式媒体路径。此时不调用 qBittorrent 的“删除任务及文件”。
6. 在数据库事务中把剧集的当前资源身份和 `active_download_id` 切换到新下载记录，将候选标记为 `accepted`。
7. 数据库切换成功后，仅移除旧 qBittorrent 任务，再删除回滚备份文件和旧下载记录。

数据库和文件系统不能组成同一个原子事务，因此每一步都要持久化 `replacement_stage`、旧资源路径、暂存路径和新资源路径。服务重启后根据阶段继续清理、完成文件提升或恢复旧关联，不能仅依赖进程内任务状态。

如果下载、整理或暂存验证失败，候选进入 `failed` 并记录原因，原台账、旧下载任务和旧文件保持不变，并清理替换任务产生的临时数据。

如果备份旧文件或提升暂存文件失败，候选进入 `failed`，台账仍指向旧资源；已经移动的旧文件必须恢复到原路径，残留暂存数据列为可重试清理项。

如果新文件已经成功提升且数据库切换成功，但移除旧 qBittorrent 任务、删除回滚备份、删除旧下载记录或其他残留清理失败，候选进入 `accepted_cleanup_failed`。新资源仍然是剧集的当前资源，系统保留失败项并提供清理重试；不得回滚到已经被新资源替代的旧关联。

如果旧下载记录已经被清理，系统可能没有可操作的旧任务或旧文件路径。此时人工选择新资源仍可完成下载和切换，但界面必须明确说明系统只能更新台账，无法保证删除未受跟踪的旧文件。

“保留现有资源”只把候选标记为 `kept_existing`，不删除候选审计信息，也不改变剧集状态。相同资源再次出现在 RSS 中不得重复创建待处理候选。

## 下载记录和磁盘清理语义

删除下载历史、清理 qBittorrent 任务或删除磁盘文件时：

- 不修改 `downloaded`、`marked_downloaded` 或 `ignored` 状态。
- 如果被删除记录正是 `active_download_id`，只将关联置空。
- 台账中保存的当前资源 hash、URL 和标题继续保留，不随下载记录删除。
- 后续 RSS 发现该集资源时建立人工候选，不自动重新下载。
- 只有用户选择“恢复为缺失”后，该集才能再次进入自动下载。

剧集列表默认只读数据库，不检查媒体文件是否存在。需要核对文件时继续使用显式扫描或诊断操作，避免页面浏览和周期任务唤醒硬盘。

## 数据迁移

新增表后执行一次幂等回填：

- 对每条有效集数的下载记录，按订阅偏移换算为相对集数并合并到唯一台账。
- `completed` 记录回填为 `downloaded`；存在多条时优先选择有最终重命名路径、更新时间最新的记录作为 `active_download_id`，并把所选记录的 hash、URL 和标题写入台账。
- `downloading`、`pending`、`stalled` 或 `organizing` 记录在没有已完成记录时回填为 `downloading`，选择更新时间最新的活动记录。
- 只有失败记录的集数回填为 `missing`。
- 同一集其余不同 hash 的历史记录不自动替换当前资源；可根据仍有效的资源信息建立候选，供后续人工处理。
- 不根据 `current_episode` 自动将 `1..current_episode` 全部标记为已下载，因为该字段只表示最大已收集集号，不能证明中间每集都存在。
- 无法从逐集下载记录确认的集数保持无记录或 `missing`，用户可以通过批量标记补齐已有剧集。

迁移完成后重新计算订阅的进度缓存。迁移必须可重复执行，不得创建重复台账或候选。

## API 与界面

后端需要提供以下能力：

- 获取单个订阅的剧集台账和候选摘要。
- 单集及批量修改状态。
- 获取某集的待处理候选。
- 保留现有资源。
- 使用候选资源启动人工替换任务。
- 查询人工替换任务状态和清理失败信息。

订阅页面保留现有列表入口，在每个番剧的操作中增加“剧集管理”。剧集视图使用紧凑列表或网格展示集数和状态，待人工判断的集数提供明显但不阻断正常工作的提示。资源比较界面展示旧、新标题、字幕组、语言、发布时间、hash 摘要和资源地址，并明确说明替换会在新资源成功后删除旧任务及文件。

人工替换属于破坏性操作，确认对话框必须说明旧资源删除发生在新资源完整处理之后。候选失败时界面应保留原资源仍有效的状态，并提供重试或保留现有资源操作。

## 并发与一致性

- 创建下载任务前必须在事务中锁定或原子更新对应台账，确保并发 RSS 检查不能为同一集创建两个任务。
- `(subscription_id, episode)` 唯一约束作为最终防线。
- 候选去重约束防止定时抓取重复插入相同资源。
- 完成回调只有在 `active_download_id` 仍指向当前任务时才能更新状态。
- 用户修改状态和后台完成回调冲突时，以用户明确设置的 `marked_downloaded` 或 `ignored` 为准，后台不得覆盖。
- 同一集同一时间只允许一个 `replacing` 候选；其他候选保持 `pending`。

## 错误处理

- RSS 抓取失败不改变台账、候选或换源基线状态。
- 下载任务创建失败时，台账保持或恢复为 `missing`。
- 重命名失败时保留下载记录和 `downloading` 状态，不删除旧资源。
- 候选写入失败不能触发自动替换，错误应记录并在后续抓取重试。
- 用户人工状态更新失败时不执行后续 qBittorrent 或文件操作。
- 旧资源清理采用可重试的显式状态，避免数据库已经切换但错误被日志吞掉。
- 服务启动或替换任务查询时检查未完成的 `replacement_stage`，把中断流程恢复为可继续、可重试或需要人工介入的明确状态。

## 测试范围

### 模型与仓储

- 同一订阅同一相对集数只能创建一条台账。
- 不同语言、字幕组、版本和 hash 仍映射到同一台账。
- 下载记录删除只清空活动关联，不删除台账。
- 候选资源可幂等写入并保持人工处理结果。

### RSS 与换源

- `missing` 集数正常自动下载并进入 `downloading`。
- `downloading`、`downloaded` 和 `marked_downloaded` 遇到不同资源只创建候选。
- `ignored` 不自动下载也不创建普通候选。
- RSS 地址变更后首次同步不回灌历史缺集，但会为已有集数建立差异候选并重设水位线。
- 换源后的新发布缺失集数仍能正常自动下载。

### 完成与失败

- 重命名成功后才标记 `downloaded`。
- 重命名失败保持 `downloading`。
- 下载失败或取消只在任务仍为当前关联时恢复 `missing`。
- 重复完成回调保持幂等，不覆盖人工状态。

### 人工替换

- 新资源失败时旧任务、旧文件、旧下载记录和剧集关联全部保留。
- 新资源成功写入暂存路径后才移动旧文件；正式文件提升和数据库切换成功后才确认替换完成，失败时旧文件可从回滚路径恢复。
- 旧资源清理失败时保留明确的可重试状态。
- 同一集不能并发启动两个人工替换。

### 迁移与界面

- 迁移正确合并同集多条历史下载记录，并且重复运行不产生重复数据。
- 迁移不根据最大集数推断中间集已下载。
- 用户可以单集和批量标记、恢复及忽略。
- 剧集页面加载和状态修改不访问媒体磁盘。

## 验收条件

- 系统中不存在任何基于语言、字幕组、版本或 hash 的自动同集替换路径。
- 已下载或手动标记的剧集遇到新资源时，旧资源保持不变并出现待人工处理候选。
- RSS 地址变更不会清空台账，也不会自动回灌新源历史资源。
- 用户选择替换时，新资源失败不会影响旧资源；新资源成功后旧任务和旧文件才被删除。
- 清理下载历史、qBittorrent 任务或文件不会让已下载剧集重新进入自动下载。
- 缺集、进度和完结状态以剧集台账为事实来源，并正确处理集数偏移。
- 常规剧集管理不依赖同步文件系统检查。
